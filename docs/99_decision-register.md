# 検討事項リスト（Decision Register）

> このプロジェクトの「決め事の台帳」。確定事項の索引と、保留事項のトリガー（着手条件）を一元管理する。
> 考慮漏れを防ぐ仕組みそのもの。Claude Code 移行後も、これを見れば「次に何を考えるべきか」が分かる。

---

## ドキュメント構成（命名規則）

移行用ドキュメントは以下の5枚。番号プレフィックス＋英語ケバブケースで統一。

| ファイル | 役割 |
|---|---|
| `01_project-overview-scope.md` | プロダクト概要・スコープ（背骨） |
| `02_architecture.md` | アーキテクチャ・データ仕様 |
| `DESIGN.md` | UI憲法（melta-ui取り込み＋固有差分） |
| `04_harness.md` | AI駆動の進め方（ハーネス） |
| `99_decision-register.md` | 本書（決め事の台帳） |

- **`03` 枠は `DESIGN.md` が担う**（番号付き `03_design.md` にせず、melta-ui／各AIツールが慣例的に探す `DESIGN.md` をそのまま使うための意図的な例外）。
- 各ファイル冒頭に他ファイルへの参照（地図）を置き、1ファイルを薄く保つ。全部を1ファイル（CLAUDE.md等）に詰めない。
- 配置は確定：`CLAUDE.md`・`DESIGN.md`・`README.md` はルート、`01/02/04/99` は `docs/`（確定事項の索引参照）。
- `README.md` は最小stub作成済み（完全版は保留事項）。

## 運用ルール（考慮漏れを取り込む仕組み）

1. **新しい検討事項が浮かんだら、その場で解決しようとせず、まず本リストに「項目名＋トリガー」だけ書いて預ける。** 今の作業は中断しない。トリガーが充足したら「次に着手可能」として浮上する。
2. **トリガーは「時期」でなく「状態」で書く**（例：「2役が安定稼働してから」）。
3. **ブロック（区切り）の変わり目で一度だけ点検する**：「リストに足すべき新項目はあるか？」。毎回は問わない。
4. 確定したら結論を追記し、状態を「確定」に。土台に属する確定事項は該当ドキュメントへ転記。
5. **過去の経験は判断材料であって制約ではない。** 同じ技術等を再採用する場合はオーナーが明示的に宣言する（「前に使ったから」で積み上げない）。
6. **節目で「全量点検」を行う**（ブロックの変わり目・フェーズ移行）。漏れを後から拾うだけでなく、**全量マップ（`ADR-0004` の領域A〜H）に上から照らして出し切る**。追加はMVP→スクラム的改良の中で扱い、思いつきの継ぎ接ぎを禁ずる。＝本台帳は「バックログ」（下記）。

---

## 合意形成フロー（確定）

検討事項リストが「次に着手可能な項目」を示す → 1ブロックずつ叩き台→オーナー判断→合意 → 結論を追記し状態更新 → 次項目のトリガーが充足 → 「次」が自動更新。
このサイクル自体が進め方。リストを見れば「今ここ・次これ」が常に分かる。
