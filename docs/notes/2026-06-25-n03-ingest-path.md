# N03投入の登場人物と流れ／ローダの置き場所 (2026-06-25)

> 壁打ちで「PostGIS への投入が取得から何をするのか／ローダをどこに置くと何が違うのか」を、地理空間の周辺知識ゼロ前提で並べ直した保存。採用判断＝`ADR-0023`、投入機構の骨格＝`ADR-0022`、お作法＝`backend-conventions` §5。前提（投入工程・シェープ・SRID）は `docs/notes/2026-06-25-n03-ingest.md`。

## 学んだこと

### 登場人物（カタログ）
- **N03（行政区域データ）**＝区市町村の輪郭ポリゴン＋コード/名称。結合の的。
- **国土数値情報サイト**＝N03 の配布元。MLIT API とは別物で、年度別・都県別ファイルを直リンクで落とす。
- **シェープファイル**＝N03 の配布形式。`.shp`(図形)/`.dbf`(属性表)/`.prj`(座標系)… 複数ファイルで1セット。
- **ローダ**＝シェープを読んで PostGIS のテーブルへ流し込む変換器。`shp2pgsql`(専用)と `ogr2ogr`(汎用)の2択。目的はどちらでも達成可能。
- **GDAL**＝地理データ変換の世界標準ライブラリ。`ogr2ogr` はその一コマンド。
- **PostGIS（DBコンテナ）**＝最終格納先。docker-compose で常駐している PostgreSQL＋地理拡張。
- **Docker のイメージ／コンテナ**＝イメージは「道具一式の設計図」、コンテナは「それを起動した実行中の実体」。同じイメージから何個でも起動できる。
- **`admin_unit` テーブル**＝正規化後の最終格納先（段0で空のまま作成済み）。

### EPSG:6668 とは
座標系（地球上の位置を緯度経度でどう測るかの基準）の通し番号。**6668＝JGD2011（日本の緯度経度の最新基準）**。保存はこれに統一する（`ADR-0014`）。N03 の元データが 6668 以外なら投入時に 6668 へ変換する。元の座標系は `.prj` に書いてある＝だから実ファイルを見る。

### 取得から投入までの全工程
```
工程0 DB起動済み
工程1 取得    国土数値情報サイトから東京都(13)のN03を落とす → 解凍
工程2 素性確認 .prj(座標系)・.dbf(文字コード)を実際に見る ← 憶測しない
工程3 投入    ローダでシェープを生テーブル n03_raw へ(座標系→6668・文字コード指定)
工程4 正規化  SQL/Go で 5桁コード抽出・年度固定・値域チェック → admin_unit
工程5 検証    reviewer が層1(データの正しさ)を確認 → dev
```
ローダ選び・置き場所が影響するのは**工程3だけ**。工程4以降（本丸）には波及しない＝継ぎ目（`ADR-0022`/`ADR-0015`）。

### ローダの置き場所（案A/B/C）と「汚さない」の意味
ローダは DB の外で動く道具で、ネットワーク越しに DB へデータを送るだけ。だからローダと DB は別の場所に居てよい。置き場所が3案:
- **案A 使い捨て別コンテナ**＝投入時だけ GDAL 公式イメージから `docker run --rm` で立て、DBへ流し、終わったら捨てる。**DBイメージは公式のまま**。
- **案B DBイメージに同居**＝`FROM postgis/postgis` ＋ `apt install gdal-bin` で焼き込む。DBコンテナ内に道具が常駐。localhost接続で楽だが公式から乖離。
- **案C 端末直インストール**＝再現性ゼロで却下。

**「汚さない（案A）」の見返り**は4つ：(1) 再現性＝DBは公式そのまま・誰の端末でも同じ (2) サイズ＝GDAL一式をDBに足さない (3) 攻撃面＝常駐DBに余計なソフトを入れない（`net/http`/Biome の攻撃面最小の軸と同じ） (4) 役割分離＝「DB=保管／ローダ=投入の道具」を混ぜない。代償は接続とマウントを一度設定する手間だけ。

### GDAL公式イメージとは
OSGeo（地理系オープンソースの団体）が GDAL を全部入れて配布している既製の Docker イメージ＝`ghcr.io/osgeo/gdal`（`ghcr.io`＝GitHub のコンテナ置き場）。**ogr2ogr が確実に入った、保守された道具箱コンテナ**。案A で「ローダ入りの別コンテナ」を用意するとき、自作せず蛇口をひねるだけで済むので素直。`shp2pgsql` だけの定番既製イメージは乏しく、欲しければ自作の手間＝これが「ogr2ogr に寄せる」の中身。

## なぜ重要 / どこで効く
- 段1（ETL縦スライス）の入口＝N03 投入の実装そのものに直結。工程3 のコマンド形と docker-compose の構成（ingest 用の使い捨てサービス／`docker run --rm`）がここで決まる。
- 「道具と土台を分ける（案A）」は、`net/http`/Biome/標準ServeMux と同じ**攻撃面最小・薄く保つ**の軸を、実行環境のレベルでも貫く判断。判断軸の一貫性として効く。
- 「実ファイルを見てから引数を決める（工程2）」は F-001（憶測で状態を断定しない）の運用。
