# 災害の「該当面積率」を地図に出すまで — 地図の計算をゼロから解説 (2026-07-05)

> **この note のねらい**：洪水などの災害を「区の何％が危険区域に入っているか」で地図に色分けする仕組みを、地図の計算（GIS）を全く知らない人が読んでもレビューできるよう、**出てくる言葉の意味から**説明する。実装＝スライス #74（洪水 XKT026）、設計の根拠＝`ADR-0006`（災害＝該当面積率）/`ADR-0015`（交差面積按分）/`ADR-0014`（座標系）/`ADR-0032`（配色）/`ADR-0030`（エリア拡張）。

---

## 1. この指標が答えたい問い

**「この街（区・市）は、面積のどれくらいが洪水の浸水想定区域に入っているか」** を割合（%）で表す。

例：ある区の面積のうち、洪水浸水想定区域に重なっている部分が全体の45%なら「洪水該当面積率 = 45%」。地図では、その数字が大きい区ほど濃い色で塗る。

- **なぜ「面積率」か**（`ADR-0006`）：浸水の「深さ」や「危険度」を点数化せず、**事実（該当する面積の割合）だけ**を見せる。「水深5mは0.5mの何倍危険か」といった主観的な重みづけをしない（客観性が崩れるため）。深さは将来、別の見せ方で足す。
- **なぜ災害から**：災害は住み替えで誰もが気にする共通の関心事であり、「面（エリア全体）と将来で比べる」という本プロダクトの差別化の核。

---

## 2. この note に出てくる言葉の意味

先にここで全部説明する。以降はこの意味で使う。

- **ポリゴン**：地図上の「面（区域）」を、輪郭の点（座標）をつないで表した多角形。**区の形**も**浸水想定区域**も、どちらもポリゴン。
- **座標系 / EPSG:6668 / JGD2011**：地球上の位置は緯度・経度の数字で表すが、その数字を**どの基準で測るか**にはいくつか種類があり、基準が違うと同じ場所でも数字が数十メートルずれる。この基準の種類には世界共通の通し番号（**EPSG コード**）が振られている。**6668 番＝日本の最新の基準（名前は JGD2011＝日本測地系2011）**。データごとに基準がバラバラだと図形が正しく重ならないので、本プロジェクトは**すべてのデータを 6668 に統一**している（`ADR-0014`）。
- **geom（ジオメトリ）**：地図上の図形（点・線・面）そのもののデータ。データベース（PostGIS）では、テーブルの `geom` という列に図形を格納する。
- **タイル（z / x / y）**：地図を格子状に区切った1枚1枚の四角。`z`＝ズーム（数字が大きいほど拡大＝1枚が狭い）、`x`/`y`＝格子の位置。広い範囲を扱うには、多数のタイルを1枚ずつ集める。
- **GeoJSON**：図形（ポリゴンの座標や属性）をテキストで書いたファイル形式。1タイル分の浸水想定区域が GeoJSON で返ってくる。
- **PostGIS**：データベース（PostgreSQL）に「地図の計算」を足した拡張。面積・交差・結合といった図形の計算を、命令（SQL）で実行できる。
- **交差（`ST_Intersection`）**：2つの面が重なっている部分を取り出す計算。「区の面」と「浸水想定区域の面」が重なる領域。
- **結合（`ST_Union`）**：ばらばらのポリゴンを1つの面にまとめる計算。重なりを溶かして1枚にする。
- **面積（`ST_Area`）**：図形の面積を測る計算。
- **`internal/tilegrid`**：このプロジェクトで自作したプログラム部品。「この範囲（例：東京都）を覆うにはどのタイル（z/x/y の組）が何枚要るか」を計算して一覧を出す。地価・人口の取得でも使った共通部品。
- **self-source（セルフソース）**：取得スクリプトが実行時に、リポジトリの外に置いた設定ファイル（APIキーなど）を**自分で読み込む**書き方。キーをコードに書かず、画面にも出さない（秘匿の死守）。
- **レート制御**：APIに一度に大量のリクエストを送るとサーバに負荷や制限がかかるので、**1枚取るごとに少し待って**間隔を空けること。
- **冪等（べきとう）**：同じ処理を何回実行しても結果が同じになる作り。途中で失敗して再実行しても、二重に登録されたりしない。
- **雛形（ひながた）を再利用**：地価・人口の取得スクリプト（`scripts/fetch-xpt002.sh`・`fetch-xkt013.sh`）が既にあり、「鍵の読み込み方・タイルを1枚ずつ取る繰り返し・待機の入れ方」がそこに書いてある。それを下敷きにして洪水用（`fetch-xkt026.sh`）を作る＝ゼロから書かない、という意味。

## 3. 全体の流れ（取得 → 格納 → 算出 → 保存 → 表示）

```
[MLIT API]
   │  タイルを1枚ずつダウンロード（約6960枚・§7）
   ▼
[data/xkt026/ … ダウンロードした GeoJSON ファイル群]
   │  データベースへ取り込み
   ▼
[PostGIS の flood_polygon テーブル … 浸水ポリゴンの置き場（新設）]
   │  区ごとに「結合 → 交差 → 面積」を計算（本丸・§4）
   ▼
[PostGIS の metric_value テーブル … 区ごとの「該当面積率 %」を1行]
   │  API（/api/choropleth/values）で配信
   ▼
[地図 … 青の濃淡で面塗り＋凡例（データが無い区は色を塗らない）]
```

各段の説明：

1. **取得**：スクリプトが `internal/tilegrid`（§2）で「1都3県を覆う z14 タイルの座標一覧」を計算し、API から1枚ずつ GeoJSON をダウンロードする。APIキーは self-source（§2）でヘッダに渡し、値は画面に出さない。枚数が多いのでレート制御（§2）で間隔を空ける。
2. **格納**：ダウンロードした GeoJSON の中の浸水ポリゴンを、PostGIS の `flood_polygon` テーブルに入れる（座標系は6668）。**なぜデータベースに入れるのか**：面積・交差・結合は PostGIS の計算機能で行う＝図形がデータベースに入っていないと計算できないから。
3. **算出（本丸）**：区ごとに、その区に重なる浸水ポリゴンを集め、**まず結合（`ST_Union`）で1枚にまとめてから**、区と交差（`ST_Intersection`）させ、交差した部分の面積を測り、区全体の面積で割る（→ §4・§5）。
4. **保存**：計算結果を `metric_value` テーブルに1行入れる（区のコード・該当面積率・出典・年度）。浸水域が無い区は「該当なし＝0%」、取得できていない区は「データなし」として区別する（→ §6の判定基準）。
5. **表示**：フロントエンドが % を取得し、青の濃淡で区を塗る。凡例を出す。データが無い区は色を塗らず、下の地図を透かす。

## 4. いちばん大事：なぜ「分割された浸水ポリゴンの結合」が要るか

ここが層1（データの正しさ）の核心。

- タイルは地図を**格子で切る**。だから1つの大きな浸水域が、複数のタイルにまたがって「別々の断片」に切られて届く。
- さらに境界付近では、断片どうしが**わずかに重なる**ことがある（API が大きなポリゴンを分割して提供する都合・XKT026 の仕様注記）。
- もし各断片の交差面積を**そのまま足し算**すると、重なった部分を**二重に数えて**しまう＝面積率が実際より大きくなる（**100% を超える**ことさえある）。

```
       タイルの境界
         │
  ▓▓▓▓▓▓▓│▓▓▓▓        1つの浸水域が、タイルで2つの断片に切られる
         │
そのまま足す： ▓▓▓▓▓▓▓ ＋ ▓▓▓▓ → 境界の重なりを二重に数える → 面積が過大
結合してから： ▓▓▓▓▓▓▓▓▓▓▓（1枚に溶かす）→ 正しい面積
```

だから、区に重なる浸水ポリゴンを**全部集めて結合（`ST_Union`）で1枚に溶かしてから**面積を測る。
→ **確認方法**：もし面積率が 0〜100% に収まらず 100 を超える区が出たら、この結合が漏れているサイン（§8）。

---

## 5. なぜ緯度・経度のまま面積を測らないか

- 緯度・経度は「度」という単位。日本では**経度1度と緯度1度の実際の長さが違う**（地球は丸いため）。度のまま面積を計算すると、実際の㎡から歪む。
- PostGIS には **geography（ジオグラフィ）という測り方**があり、地球を球面として扱って正しく㎡で測る。既存の「市区町村の面積（area_km2）」も同じ方法を使っている。
- ＝面積率の**分子（重なった面積）も分母（区全体の面積）も geography で㎡を測り**、割る。座標系は6668で一貫させる。

**「区面積で割って%」を正確に言うと**：区に重なる浸水面積 ÷ 区全体の面積 で割合（0〜1 の数）を出し、それに 100 を掛けてパーセント（%）で表す。例：割合が 0.45 なら 45%。

## 6. 「該当なし（0%）」と「データなし」をどう見分けるか

この2つは意味が違い、混同させない（`ADR-0011`）。判定は次の2点で決める：

| その区の状態 | 意味 | metric_value の記録 |
|---|---|---|
| タイルを取得できて、中に浸水ポリゴンが1つも無い | 浸水想定が本当に無い | 値 = 0、状態 = `present`（＝「該当なし＝0%」） |
| タイルの取得をまだやっていない／取得に失敗した | データが揃っていない | 値 = なし、状態 = `none`（＝「データなし」） |

- ＝**「取得できたか（成功/失敗）」×「取得の中身が空か（浸水ポリゴンが0件か）」** の組み合わせで決める。
- 表示側では、`present`（値0を含む）は色を塗り、`none` は色を塗らない（下の地図を透かす）＝「危険ゼロの街」と「まだ調べていない街」が見た目で区別される。

## 8. 規模のイメージ（なぜ「重い」のか）

- XKT026 は **z=14〜15 でしか配られない**（API の制約）。面積率のために広い範囲の**全タイル**が要る（低いズームで粗く取る逃げ道がない）。
- z14 で1都3県（東京・埼玉・千葉・神奈川）＝**約6960枚**。1枚ずつ、レート制御で間隔を空けて取ると**約1時間**。
- 参考：人口（XKT013）は z11・**24枚**で済んだ。＝桁違いに多い。洪水は「取得が重い指標」。
- だから取得は冪等（§2）に作る＝途中で失敗しても、もう一度流せば同じ結果になり、二重登録もされない。

## 9. レビューの勘所（何を・どこで見れば正しさが分かるか）

層1（データの正しさ）は、次を**具体の操作で**確認する：

- **面積率が 0〜100% に収まっているか**：
  `SELECT min(value), max(value) FROM metric_value WHERE metric='flood_area_coverage_rate';`
  → max が 100 を超えていたら、分割ポリゴンの結合漏れ（§4）。
- **浸水域が無い区が「0%・present」になっているか**：
  内陸で浸水想定が無いはずの区を1つ選び、その行が `value=0, status='present'` か。`status='none'` なら誤り（§6）。
- **取得していない区が「データなし・none」になっているか**：対象外エリアの区が `status='none'` か（§6）。
- **座標系が6668で一貫しているか（＝どこで分かるか）**：
  `SELECT DISTINCT ST_SRID(geom) FROM flood_polygon;` が **6668 だけ**を返すか。区の側（admin_unit）も6668か。違う番号が混じると交差計算がずれる（§2・§5）。
- **出典が保持されているか**：`metric_value` の `source` 列に XKT026 の出典（国土数値情報 洪水浸水想定区域…）が入っているか（法的要件・`ADR-0011`）。
