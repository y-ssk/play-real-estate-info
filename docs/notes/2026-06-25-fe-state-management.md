# FEの状態管理：サーバ状態とクライアント状態・ZustandとJotai (2026-06-25)

> 採用＝`ADR-0018`（TanStack Query＋Zustand）。本メモは「なぜ」と、**技術選定・ライブラリ導入の考え方**の蓄積が目的（とくに Jotai を落とした理由を手厚く）。

## 学んだこと

### 1. サーバ状態とクライアント状態は別物（混ぜない）
現代FEの定石。状態を出自で2分する。
- **サーバ状態**＝APIから取ってきたデータ（地価の値・カルテ・絞り込み結果）。**いずれ古くなる**ので、キャッシュ・再取得・読み込み中/失敗・重複排除が要る。「手元のコピー」。
- **クライアント状態（UI状態）**＝サーバ由来でない画面の状態（選択中の指標/分野/単位・絞り込み条件・パネル開閉・ピン）。サーバと同期する必要がない。
- **なぜ混ぜないか**：サーバ状態に要る「再取得・古さ判定」は UI状態には不要で、UI状態を汎用ストアに置いてサーバデータも同居させると、キャッシュ無効化・競合処理を自前で作る羽目になる（＝自前fetchの罠）。役割の違う2つに、役割の違う道具を当てる。

### 2. 取得ライブラリ（サーバ状態）
- **TanStack Query（採用）**：取得の事実上標準。キャッシュ・再取得・loading/error・古さ(stale)を宣言的に（やり方でなく「こうあるべき」を書く）。「指標切替→`values`だけ再取得・`geometry`はキャッシュ維持」「街選択→`karte`取得」が素直。
- **守備範囲はタイル化で縮む**：行き先A（`ADR-0016`）でベクタタイル化すると **geometry/タイルは MapLibre が自前取得**（内部処理）。Query が司るのは JSON系（`values`・`karte`・絞り込み）だけになる。初手B（GeoJSON）期は geometry も JSON なので Query が持てる。＝Query の本体価値は「JSONデータの取得管理」で B→A をまたいで安定。
- **欠損/出典UI（`ADR-0011`）と噛む**：loading/error/empty の一貫モデルが、データなし3区別（データなし/該当0/秘匿）の表示に対応。
- 対案：SWR（同思想で軽量）、自前fetch（再発明・✕）、RTK Query（Redux前提＝過剰）。

### 3. クライアント状態の道具 ― Zustand と Jotai（ここを手厚く）

#### 根本の違い：「上から1つの箱」 vs 「下から小さな粒」
- **Zustand（採用）＝store型**：1つ（か少数）のストアに状態をまとめ、`useStore(s => s.x)` の **selector で必要部分だけ購読**（x が変わった時だけ再描画）。Redux系譜を極小化した発想。**Provider不要**（モジュールレベルのストア）。
- **Jotai＝atom型**：状態を**最小単位の atom に分解**し、atom を組み合わせて（派生atom）使う。Recoil系譜。`<Provider>` は任意（スコープ用）。

#### なぜ Jotai が有力候補なのか（公平に）
1. **atom単位で購読**＝再描画が自然に最小化、派生atom（既存atomから計算する atom）で依存が綺麗に書ける。
2. **URL/localStorage同期のユーティリティが宣言的**（`atomWithStorage`・`jotai-location`/`atomWithLocation`）。「選択指標」「選択単位」を独立atomにして URL と双方向同期、が書きやすい。
3. 多数の細粒度状態・複雑な派生関係に強い。コード分割とも相性。

#### なぜ本件で Jotai にしないか
1. **共有UI状態が少数**（選択指標/分野/単位・絞り込み・パネル開閉・ピン）＝単一storeで一望でき、atom分割の粒度設計コストが、得られる最小再描画の利得を上回らない。**Zustand も selector で部分購読でき再描画は絞れる**ので、「再描画最小化」は Jotai 独自の決め手にならない。
2. **MVPの状態は「画面横断の少数のグローバル値」**で、Jotai の強み（多数の細粒度atom・複雑な派生）が要る局面が薄い＝周辺は薄く（CLAUDE.md）。
3. **永続化が素直**：Zustand `persist` はストア丸ごと localStorage に同期（ピン＋選択をまとめて）。Jotai は atom ごとに storage 設定で、まとめるなら一手間。
4. **学習・レビューの単純さ**：1ストアは「どこに何があるか」が一望。atom が散ると規約なしには追いにくい。

#### 再評価のトリガー（可逆な決定・`ADR-0013`）
**URL状態を MVP で本格採用**、または**状態が細粒度・多数・複雑な派生に育つ**なら、Jotai が優位に転じうる。乗換コストは中程度なので、今は問題形状に最小の道具（Zustand）を当て、形状が変わったら再評価する。

### 4. 技術選定・ライブラリ導入の一般則（高品質インプット）
- **「道具の優劣」でなく「強みが“いまの問題形状”に当たるか」で選ぶ**。Jotai の強み（細粒度/派生/URL同期）は強力だが、MVPの「少数の横断グローバル値」には過剰。優れた道具でも問題に当たらなければ採らない。
- **可逆性を判断軸に入れる**（`ADR-0013`）。乗換が安いなら、将来を見越して重い道具を先に入れるより、今に最小の道具＋形状変化での再評価が合理。
- **ただし構造的に大きい変更の継ぎ目は今作る**（MVP集中≠v1無視）。下記の識別子がその実例。

### 5. 識別子に粒度を内蔵する継ぎ目
- **選択中の単位は `{unit_kind, unit_id}` で持つ**（Zustand・Query のキャッシュキー・将来のURL）。裸の市区町村コードにしない。
- なぜ：v1 で集計単位が市区町村→250mメッシュに降りると粒度が変わる（`ADR-0015` の `unit_kind`）。裸のidだと URL/キャッシュ/選択が粒度移行で壊れる/曖昧になる。粒度を識別子に内蔵すれば、store も URL も作り直さずに済む。`ADR-0016` の「値/形分離の継ぎ目」と同じ発想。
- Query のキャッシュキーにも `unit_kind` を含め、粒度違いでキャッシュが衝突しないようにする。

## なぜ重要 / どこで効く
- 状態を出自で2分し別の道具を当てるのが、再取得・キャッシュ・失敗処理を自前で書かずに済む最短路。
- Jotai を落とした理由は「問題形状との適合」で、これは今後の他のライブラリ選定にもそのまま使える物差し。
- 識別子の継ぎ目は、メッシュ移行という構造的に大きい v1 変更を MVP の手戻りなしに迎えるための先行設計。
