# ドキュメンテーションとコメントの作法：WHAT でなく WHY (2026-06-25)

> 採用＝`backend-conventions.md` §3／`frontend-conventions.md` §6。本メモは「なぜその線引きか」の蓄積。

## 学んだこと

### 「コメント入れすぎるな」と「複雑な処理は説明したい」は、量でなく中身で両立する
- **WHAT（コードを読めば分かること）のインラインコメントは書かない**＝コードと二重で、すぐ陳腐化する。「入れすぎるな」が正しいのはここ。
- **WHY（意図・非自明な理由・落とし穴・なぜこの式か）は書く**＝「複雑な処理は説明したい」が正しいのはここ。
- 線引きは**量でなく WHAT/WHY**。複雑＝コメント多、ではない。

### 公開したものには doc 注釈、内部は WHY のみ
- **エクスポート（公開）した関数・型・コンポーネントには doc 注釈を必須**＝外から使われる窓口だから（ツールのホバー表示・生成ドキュメントから引ける）。
- **内部（非公開）は doc 必須にしない**（必要時に WHY コメントのみ）。内部まで doc 必須にすると WHAT の繰り返しで形骸化する。

### 言語ごとの仕組み
- **TypeScript（JSDoc/TSDoc 流）**：**型を doc に重複させない**（型はシグネチャにある＝TS の強み。`@param {string}` 式は不要）。doc は説明・`@example`・`@see`・`@deprecated` を担う。**日本語で**書く。
- **Go（godoc）**：doc コメントは**識別子名で始める**（`// MetricValues は…`）。`go doc`／pkg.go.dev が表示。パッケージコメントも1つ。**機械可読の注釈＝struct タグ**（`json`/`db`）＝API 応答・sqlc/pgx の対応付け。
- **強制**：エクスポート識別子の doc は lint で要求できる（Go＝revive の exported ルール）＝lint と連動。

## なぜ重要 / どこで効く
- 「コードを補佐する＝何をしているか分かる」を、陳腐化しない形（公開＝doc、複雑＝WHY）で実現する。
- 複雑なドメイン処理（空間集計の按分・コード/座標の正規化・指標算出）は WHY＋ADR/学習メモへのリンクで、根拠まで辿れる。
