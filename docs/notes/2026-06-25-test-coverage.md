# テストカバレッジ：何か・何を保証しないか・本プロジェクトの方針 (2026-06-25)

> 採用方針は本メモ末尾＝`docs/99` で確定（a/b/c）。conventions のテスト章へ反映予定。

## 学んだこと

### カバレッジとは
テストを実行したとき、製品コードの「**どこが実際に通ったか**」を測った割合。「テストした量」ではなく「**テスト実行中に走ったコードの割合**」。

### 測る対象の種類（粗い→細かい）
- **行/文（line/statement）**：何行・何文が実行されたか。最も粗い（通っただけで論理は見ない）。
- **分岐（branch）**：`if`/`switch` の各枝（真も偽も）を通ったか。**論理の網羅に近い**。
- **関数（function）**：各関数が呼ばれたか。粗い見取り図。
- **条件/MC-DC**：複合条件の各項の真偽の組合せ。航空宇宙級・MVPには過剰。
- **パス（path）**：経路の全組合せ。組合せ爆発で非現実的。

### 何を教え、何を保証しないか（肝）
- **教える**：「どこが一度もテストで実行されていないか」＝**未テストの空白を見つける道具**。
- **保証しない**：①テストが意味ある検証をしているか（`assert` 無しでも%は上がる）。②100%でもテストしていない入力のバグは残る。
- → **「テストの不在」を可視化するが「テストの質」は保証しない**。「高い＝良い」ではなく「**低い＝赤信号（未テスト領域あり）**」というアラート寄りの使い方が正しい。

### アンチパターン
- **%を目標にする**（Goodhartの法則＝指標が目標になると指標として壊れる）。`assert` 無しや trivial コードで%を盛る。
- **一律グローバル%ゲート**：本丸も周辺（getter・設定）も同じ基準で塗り、周辺の薄いテストを量産して本丸が埋もれる。`docs/01`「網羅でなく“仕組みが正しく動くと確かめる”」に反する。

## なぜ重要 / どこで効く（本プロジェクトの方針＝確定）
- **(a) 計測・可視化はするが、当面はゲート（閾値で落とす）にしない**。`go test -cover`／Jest `--coverage` で出す。
- **(b) 本丸に絞って見る・分岐カバレッジを重視**：層1（ETL変換・空間集計・動的フィルタ組み立て／FE は状態ロジック・出典/欠損表示・識別子）の**分岐**を見る。周辺（DTO・設定）の%は追わない。
- **(c) 差分カバレッジ（diff coverage＝今回の変更行が新たにテストされたか）を主signal**：グローバル%は参考に留める。`reviewer` 層2に「**本丸の変更に分岐テストがあるか**」を入れる。
- ゲート化（閾値で落とす）は CI 着手時に再検討。
- 根拠：`docs/01`（網羅でなく仕組みが動くこと）・`docs/04`（Feedback層1＝データの正しさ）・`ADR-0011`（データなし3区別の検証）。
