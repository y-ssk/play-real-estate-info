# 地図の形の運び方：GeoJSON とベクタタイル（MVT/pbf）・タイル座標 (2026-06-24)

## 学んだこと

### 面を塗るのに要るのは2つだけ
ブラウザの地図(MapLibre)が市区町村を指標で塗るには、(1)形＝各区ポリゴンの座標、(2)値＝各区の指標数値、の2つだけ要る。地図は「値→色」の対応表で塗る。論点は「(1)の形をPostGISからどう運ぶか」に尽き、(2)値と色付けは運び方に依らず同じ。

### GeoJSON＝テキストで形を運ぶ
地理的な形を表すJSONの形式。ポリゴンは経度・緯度ペアの並びを素のテキストで書く（並びは`[経度,緯度]`＝x,y順で、口語と逆。落とし穴）。座標は実世界の経度緯度・フル精度。**一塊で運ぶ**＝全区のポリゴンを1応答に全部入れる。読める・`curl`で目視できる・単純だが、形が多い/細かいと重い（メッシュ数十万件をテキストで送ると巨大）。
- PostGIS関数 `ST_AsGeoJSON(geom)` がジオメトリをGeoJSON文字列にする。＝「形をテキストでまるごと吐く」。

### タイル＝世界を正方形の格子に切って見える分だけ送る
オンライン地図は世界全体を毎回送れないので、地図を正方形タイルの格子に切り、見えているタイルだけ送る。格子はズームレベル`z`で段階的に細かくなる（z=0は世界1枚、一段ごとに縦横2倍、z=nは2^n×2^n枚）。各タイルは`z`(ズーム)/`x`(列)/`y`(行)の3数字で住所が決まる（例 `/tiles/10/909/403.pbf`）。地図ライブラリは見えているz/x/yを計算しそのタイルだけ取り、離れたら捨てる＝何件あっても見える分しか持たず軽い。

「タイル座標の山」＝これに付く新しい考え方の一束：経度緯度↔z/x/yの相互変換（`ST_TileEnvelope(z,x,y)`がそのタイルの覆う範囲を返す）／多数の小タイルを取りに行く動き／各タイルが形を縁でクリップ／タイル内座標は経度緯度でなく0〜4096の局所整数目盛り。

### MVT/pbf＝タイルの中身の形式
- **MVT(Mapbox Vector Tile)**＝1枚のタイルの中身を表す標準形式。そのタイルに入る形だけを、座標を0〜4096の局所整数で持つ。
- **pbf**＝そのMVTをProtocol Buffers(Google由来)で詰めた**バイナリ**。小さく速いが**人は読めない**（`curl`してもバイト列）。
- PostGIS関数 `ST_AsMVT` がタイル範囲内の形を集めてpbfを作る。SQLの骨子：
  ```sql
  SELECT ST_AsMVT(t) FROM (
    SELECT unit_id, ST_AsMVTGeom(geom, ST_TileEnvelope(:z,:x,:y)) AS geom  -- クリップ＋局所目盛りへ
    FROM boundaries WHERE geom && ST_TileEnvelope(:z,:x,:y)                 -- このタイルに触れる形だけ
  ) t;
  ```

| | `ST_AsGeoJSON` | `ST_AsMVT` |
|---|---|---|
| 単位 | 全件まとめて1回 | タイル(z/x/y)ごと |
| 形 | そのまま | タイル縁でクリップ |
| 座標 | 経度緯度・フル精度 | タイル内0〜4096整数 |
| 中身 | テキスト(読める) | バイナリpbf(読めない) |

### MapLibre のソース2種類
- **geojson source**：GeoJSONの塊(またはそれを返すURL)を渡す。全部を読み込み記憶に持って描く。形が多すぎなければ快適。→ `ST_AsGeoJSON` と組む。
- **vector source**：`/tiles/{z}/{x}/{y}.pbf` のタイルURL雛形を渡す。ライブラリが見えるタイルを自動取得・復号・描画し離れたら捨てる。件数に強い。→ `ST_AsMVT` と組む。
- 対応：`ST_AsGeoJSON`→geojson source（一塊・テキスト・全部記憶）／`ST_AsMVT`→vector source（タイル・バイナリ・見える分だけ）。色付け式はどちらも同じ。

## なぜ重要 / どこで効く
- 座標系の接続（`ADR-0014` §9）：geojson sourceは経度緯度(4326。保存6668とは実用差なし)、vector sourceのタイルはWebメルカトル(3857)で作る。`ST_TileEnvelope`も既定3857。「保存6668→配信3857」がタイルでそのまま効く。
- 「最初のETL縦スライスは極限まで薄く、タイル座標の山は後で」＝縦スライス（取得→変換→PostGIS→地図に1つ描く、を端から端まで細く通す）を、GeoJSONなら z/x/y・MVT・pbf の学習を登らずに立てられる、の意。
- 「別プロセスのタイルサーバは一体型に反する」＝`pg_tileserv`/`martin`は独立した別プログラム。使うとプロセスが2つになり、`ADR-0013`の1プロセス・単一バイナリ配備と食い違う。一体型を保つなら`ST_AsMVT`を自分のGoサーバ内ハンドラで書く。
- この理解の上で配信方式を決めた＝`ADR-0016`（継ぎ目固定／初手B GeoJSON→行き先A ST_AsMVT・一体型）。
