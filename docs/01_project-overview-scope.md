## 1. プロダクトの一文（エレベーターピッチ）

「住み替えを考え始めたが、物件の家賃や価格・間取りだけでは “その街がどういう場所で、これからどうなるのか” が分からない人」向けのエリア探索ツール。

**MachiLens**（仮名）は、不動産取引価格・地価・災害リスク・将来人口・都市計画といった公的データ（国土交通省 不動産情報ライブラリ）を地図上で重ね合わせ、自分の条件で街を調べ・比べられるツール。物件サイトが見せる “個別物件の今” とは違い、“街そのものの素性とこれから” を自分の目で確かめられる。

> **プロダクト名は仮名 `MachiLens`。** 正式名が決まり次第、全ファイルを横断検索して一括置換する。未確定であることは `99_decision-register.md` に登録。

## 2. 差別化の核 — 「物件サイトと違う観点」

物件サイトとは「見ている単位」が違う。これが価値の源泉。

- 物件サイト = **点の情報**。個別物件のスペック（価格・間取り・駅徒歩）。現在のスナップショット。
- 本プロダクト = **面の情報**。街の素性・体質・これからの傾向。

物件サイトが構造的に出せない／出さないのは、特に **時間軸（相場推移・資産性）** と **リスク・将来（災害・人口推計・都市計画）**。ここが土俵。家賃や物件の値段で張り合わない。

---

## 3. 想定ユーザーと使われ方

賃貸も含む住み替え全般。購入層と賃貸層で重視点が割れるが、共通項がMVPの軸になる。

- **購入寄り（例：子育て世帯の住み替え）**：相場・資産性・将来人口・教育環境を重視。
- **賃貸寄り（例：転勤の単身、同棲、購入資金を貯めたい層）**：今の住み心地・利便性・リスク回避を重視。資産性や将来の重みは低い。

使われ方の流れ：**広く探す（探索）→ 気になるエリアをピン留め → 数個を見比べる（比較）→ 自分で判断する**。
おすすめ（レコメンド）は土台が出来た後の機能であり、初期は「自分で調べて判断できること」を主役に置く。

### 共通項と分岐（MVPの設計指針）
- **全層が必ず見る（＝共通土台）**：災害リスク ＋ 街の利便性
- **層で割れる（＝追加レイヤー）**：相場 / 将来性（人口・都市計画） / 教育（学区・学校）

### 家賃の扱い（重要な割り切り）
公的データに「賃貸の家賃相場」は含まれない。家賃の数字は持たず、賃貸層には **街の素性（リスク・環境・利便）** で価値を出す。家賃そのものは物件サイトに委ねる。これは弱点回避ではなく「物件サイトと違う観点」という芯と一貫した判断。

## 4. 対応エリア

- **MVP：首都圏9都県** — 東京・神奈川・埼玉・千葉・茨城・栃木・群馬・山梨・静岡。
- **全国対応は希望として持つ。** ただし初手は上記に限定する（API利用条件＝連続実行を避ける、の制約と、データ品質を検証しきる現実性のため）。
- 全国化は **対象市区町村コードの「設定リスト」を拡張するだけ** で到達できる構造にする（アーキは変えない）。詳細は `02_architecture.md`。
- **段階拡張（波・`ADR-0030`）**：波1＝**1都3県**（東京13・埼玉11・千葉12・神奈川14）→波2＝**北関東**（茨城08・栃木09・群馬10）→波3＝**残り首都圏**（山梨19・静岡22）＝首都圏9都県 完成→将来＝全国。エリアは「データ操作の波」（指標＝コードとは別軸）で足し算に保つ（`ADR-0030`・`docs/99` 2軸バックログ）。

## 5. MVPスコープ

### やる
- 災害リスク と 街の利便性 を全層共通の土台として地図表示（防災レイヤー群 ＋ 駅・施設）
- 相場・将来人口・教育 を追加レイヤーとして重ねる
- 自分の条件でエリアを絞り込む検索（市区町村ごとに持つ数値・件数・有無すべてが対象。重みづけはしない）、気になるエリアのピン留め（ブラウザ保存で端末内に残す）、並べ替えできる一覧表（指標で街を並べ替え）
- 空間単位は **市区町村粒度**
- データ取り込み（ETL → PostGIS）＋ タイル配信のハイブリッド構成（詳細は `02_architecture.md`）
- データ出典の表示（MLIT／国土数値情報の利用条件。UIに最初から組み込む）

### やらない（MVPでは）
- おすすめ・スコアリング・重みづけUI（→ v2）
- 個別物件データの連携・物件検索・家賃の数字（プロダクトの芯の外）
- メッシュ粒度（250m等）（→ v1）
- エリア横並びの比較ビュー（→ v1。MVPはピン留め＋並べ替え一覧表まで）
- ユーザーアカウント・端末をまたぐ保存（→ v1。MVPのピン留めはブラウザ保存＝同一端末内で永続）
- 認証・課金・水平スケール・多言語（スコープ外）

### 今は決めない（保留）
- 外部の家賃データ連携（将来拡張・非オープン）
- ダークモード（構造上は後付け可能にしておく。詳細は `DESIGN.md`）

## 6. ロードマップ

| フェーズ | 体験 | 主な内容 |
|---|---|---|
| 構想（完了） | — | 本ドキュメント群の作成（壁打ちで設計） |
| MVP | 探索ビュー | ETL基盤 ＋ 地図 ＋ 絞り込み検索。共通土台＋追加レイヤー。市区町村粒度 |
| v1 | 比較・カルテ | エリアカルテ詳細 ＋ 比較ビュー（ピン留め横並び）＋ メッシュ粒度へ |

MVPの目的は「網羅」ではなく **「仕組みが正しく動くと確かめること」**。首都圏で意図どおりレイヤーが重なり、検索が機能するまでを完成と見なす。

## 7. プロジェクトの主目的（比重）

**学びと完成の半々。** 「AIで土台から完成までどう持っていくか」の経験そのものを重視する（特定フレームワーク習得が目的ではない）。

トレードオフの原則（リソース配分）：
- **深くやる（本丸×学び）**：取り込みバッチ(ETL)とPostGISのデータモデリング／地図上でのデータ表現
- **割り切る（既製品に乗る）**：認証・UIコンポーネント・地図描画エンジン・インフラ

期間は納期ではなく「間延びを防ぐ歯止め」として扱う。MVP内も「取り込みが先・表示が後」の順序規律を守る。
