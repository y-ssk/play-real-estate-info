# ADR-0014: 共通結合基盤の「結合の的」＝境界N03・保存SRID6668・結合キー5桁コード(区粒度)

- ステータス: 承認
- 日付: 2026-06-24
- 関連: `docs/99_decision-register.md`（優先2 共通結合基盤）／`docs/02_architecture.md` §8空間単位・§9共通前提／`ADR-0006`（集計＝単位ポリゴンへ空間結合）／`ADR-0013`（PostGIS・生SQLマイグレ）

## なぜ（背景・課題）
価値定義（`ADR-0005`〜0012）で決めた集計はすべて「単位ポリゴン（MVP＝市区町村）に空間結合して数える」共通形（面積率＝交差面積÷単位面積、地価中央値、人口増減率など。`docs/02`§8）。
この共通形が成立するには、あらゆるデータを **(A) 同じ座標系で・(B) 正しい単位ポリゴンの形に・(C) 同じ市区町村コードへ** 貼り付けられる「結合の的」が要る。ここが歪むと全分野の数値が歪むため、本丸の土台として先に固める（優先2の前半）。

着手時に台帳に無い前提も浮上した：**市区町村の「境界ポリゴン」そのものの調達先が未定**だった。`XIT002` は市区町村コードの一覧（コード＋名称）であって境界geometryを持たず、収集済みIF34本にも行政区域の境界は含まれない。面積率も点→市区町村判定も境界ポリゴンが無いと計算できないため、これを優先2先頭で決めた。

## 結論（決定）
「結合の的」を次の3点で確定する。

### (A) 単位ポリゴンの境界＝国土数値情報 行政区域データ（N03）
- 出所：国土数値情報ダウンロードサイト（国土交通省）の N03。年度別・都道府県別に配布。形式は Shapefile／GML（新版はGeoJSONも）。
- 採用理由：出典がMLIT/国土数値情報で統一でき出典表示義務と整合／測地系がJGD2011で他レイヤーと前提が揃う／`N03_007`（行政区域コード5桁）が属性で付くので結合キーが最初から手に入る。
- 「別ダウンロードのパイプライン」はボトルネックでない：実行時コストゼロ（取り込み一度→DBから返す）／更新は年1回・低頻度／API取り込みより簡単（レート制御・キー・ページング不要）／MVPは9都県のみ。そもそも境界はAPIで取れる選択肢が無く（`XIT002`はコードのみ）、どの案でもファイル取得になる＝この点は案を分けない。ハザード（XKT026系）・将来人口メッシュ（XKT013）でも「GISファイル→PostGIS」ローダは要り、N03はその最初の利用者にすぎない。

### (B) 保存SRID＝EPSG:6668（JGD2011）に統一
- 全レイヤーを `geometry(..., 6668)` で保存。大半が6668・N03も6668で変換が最小。
- 取り込み時の正規化：JGD2000(4612, XKT017/019)は `ST_Transform`→6668／CRS84(XKT027)は6668として取り込む（WGS84↔JGD2011の実用差は小、厳密変換は不要と判断・必要が出れば後追い）。
- 面積率は `geography` で算出（比なので投影差に頑健）。厳密な実面積が要る場面のみ平面直角座標系（関東＝6677等）へ投影。
- 配信（タイル／レスポンス）時に3857（必要なら4326）へ変換。MapLibre側は触らず取り込み側で吸収。

### (C) 結合キー＝5桁市区町村コード（コードを正・名称は表示用）。集計の最小単位は区粒度
- `XIT002.id`（5桁文字列）を権威マスタとし、N03 `N03_007`・各レイヤーの市区町村コード属性をこの5桁へ揃える。名称ゆれ（ヶ/ケ・大字等）は結合に使わずコードで結合。
- 値域チェック（層1）：5桁数字・上2桁＝都道府県コード(area)と一致・マスタに存在。6桁JIS（チェックデジット付き）が来たら末尾を落として5桁化。
- 年度固定：合併・改廃でコードは年度により変わるため、マスタ・N03・各レイヤーを同一年度版に揃える（MVPは最新年度）。
- 集計の最小単位は **XIT002 が返す粒度にそのまま合わせる＝政令市は区粒度**。「市でまとめて見たい」は表示・比較のグルーピングとしてUI側（v1）で後付けする。

## 検討した代替案と捨てた理由
- 境界 A2: e-Stat（国勢調査）境界 … 将来のメッシュ移行とは整合しやすいが、出典系統がMLITと別になりN03と境界の扱いに差。MVPは出典統一を優先。将来メッシュ移行時に再検討の余地は残す。
- 境界 A3: OSM／自前生成 … 精度・更新・法務/出典が不透明。本丸の土台に不適。
- 保存SRID B2: 平面直角座標系（6677等） … 面積・距離は正確だが首都圏でも系8/9をまたぎ複数系の管理が増え全国化で破綻しやすい。「保存は地理座標、面積計算時だけ投影」でB1に利点を取り込めるため保存系には採らない。
- 保存SRID B3: EPSG:3857 … 配信は楽だが面積が緯度で歪み、本丸の集計（面積率）に不適。
- 結合粒度 C-2: 政令市を「市」に畳んで集計 … 区ごとに来るデータを毎回合算する手間に加え、「同じ市でも区で街が違う」差が潰れ、面で見るプロダクトの主旨と逆行。

## 影響（結果・トレードオフ）
- 優先2前半（結合の的）が確定。残るは「空間結合の具体形（面積率SQL）」と「コード凡例収集」。
- N03 が新たな取り込みソースとして加わる（年度版の追跡・差し替えがETL更新運用に1本増える）。
- 取り込み時にCRS正規化（4612→6668等）と市区町村コード正規化（5桁化・属性名のレイヤー別マッピング）の一手間が常に乗る。
- `XIT002` が政令市で区/市どちらの粒度を返すかは実装時に実データで要確認（C-1は「返る粒度に素直に合わせる」方針なので、確認結果に頑健）。
- 後続フェーズへ預けた論点：N03ロード機構（Go ingest／ogr2ogr・shp2pgsql／ハイブリッド）と取得の自動化レベル＝ETL実装着手時／N03複製の法務注記（国土地理院長の承認）＝公開検討時。
