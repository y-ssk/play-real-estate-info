# ADR-0015: 空間結合の具体形＝事前集計(マテリアライズ)・縦持ち集計テーブル・メッシュは重心法

- ステータス: 承認
- 日付: 2026-06-24
- 関連: `docs/99_decision-register.md`（優先2 共通結合基盤・後半）／`docs/02_architecture.md` §8空間単位／`ADR-0006`（単位ポリゴンへ空間結合）／`ADR-0014`（結合の的）／`ADR-0011`（データなし3区別・出典）／`ADR-0012`（絞り込み・並べ替え一覧）／学習メモ `docs/notes/2026-06-24-spatial-join-aggregation.md`

## なぜ（背景・課題）
`ADR-0014` で「結合の的」（境界N03・保存SRID6668・5桁コード）が固まった。次は、その的へ各データを実際に貼り付けて数える「空間結合の具体形」を決める。価値定義（`ADR-0005`〜0012）の集計をSQLで書ける形にするのが目的。

集計対象はgeometryの型で3パターンに分かれる（学習メモ参照）：ポリゴン→面積率／点→件数・密度／メッシュ→集約。これらに横断して、(i)いつ計算しどこに置くか、(ii)集計結果テーブルの形、(iii)境界またぎの按分、を決める必要がある。

## 結論（決定）

### (i) 事前集計（マテリアライズ）
取り込み時に空間結合・集計を済ませ、「単位×指標」の集計テーブルへ書き出す。ユーザー操作のたびの空間結合（オンデマンド）はMVPでは採らない。
- 根拠：単位×指標は有限（首都圏 数百市区町村×指標数十＝数千行規模）と小さい／`ADR-0012` の絞り込み・並べ替え一覧は全市区町村を横断するので事前保持が軽い／ソース（ハザードのポリゴン等）は重くオンデマンド交差は高コスト／更新は年1回。

### (ii) 縦持ちの集計テーブル
`metric_value(unit_id, unit_kind, metric_key, value_num, unit, data_status, source, vintage)` の「1指標1行」。
- 根拠：指標追加が行追加で済みスキーマ変更不要／`unit_kind`・`unit_id` を差し替えればメッシュ移行が同じ表で効く（`ADR-0006`）／`ADR-0011` のデータなし3区別（`data_status`＝present/none/zero/secret）・出典・年度を行に同居できる／表示時にピボット。
- `unit_kind` は当面 `city`（将来 `mesh250`）。`value_num` は数値指標。
- **カテゴリ系（用途地域の構成比・区域区分など `ADR-0009`）は単一数値に収まらない**ため、別表（`unit_id, metric_key, category_key, value` の縦持ちのまま）で持つ案を基本とし、最終形は実装着手時に詰める。

### (iii) 演算の共通形と境界またぎ
単位ポリゴンを抽象化（`unit(unit_id, unit_kind, geom)`、市区町村↔メッシュ差し替え）した上で：
- **ポリゴン→面積率**：`Σ ST_Area(ST_Intersection(unit.geom, layer.geom)) / ST_Area(unit.geom)`（交差面積で按分）。面積は `geography` で算出（`ADR-0014`）。
- **点→件数/密度**：`COUNT(*) WHERE ST_Within(point.geom, unit.geom)`（内包判定）。密度＝件数÷面積。
- **メッシュ→集約＝重心法**：メッシュ重心が入る単位へ値を全量計上（点の内包判定と同じ仕組み）。
- 按分ルールはパターンごとに異なるのが正しい（面積=交差按分／点=内包／メッシュ=重心）。

## 検討した代替案と捨てた理由
- (i) オンデマンド空間結合 … 単位×指標が小さく更新も低頻度なのに、重いソースを操作のたびに交差させるのは高コスト。MVPでは不要。
- (ii) 横持ち（市区町村1行×指標カラム） … SELECTは単純だが、指標追加でスキーマ変更が頻発し、データなし3区別・出典・年度を指標ごとに持つとカラムが倍増、メッシュ移行で別スキーマになる。
- (iii) メッシュ面積按分 … 「人口がマス内で面積比例に均等分布」という現実に無い仮定を置き、見かけ倒れの精度。計算も重い。
- (iii) メッシュ完全内包のみ … 外周マスを捨て人口が過小になり事実をゆがめる。不可。

## 影響（結果・トレードオフ）
- 優先2が実質完了（残るは素材タスクの「コード凡例収集」）。価値定義の各指標がこの共通形でSQL化できる土台が整う。
- 縦持ちは表示時にピボットの一手間が要る／値型がnumeric統一のため、カテゴリ系の持ち方は別表で補う（最終形は実装時）。
- 重心法はメッシュ移行で不利にならない（単位とソースが同一250mグリッドに揃えばまたぎ消滅。別サイズmesh混在時のみ再考）。
- 集計の実体（テーブルDDL・集計SQL・マテリアライズの回し方）はETL実装着手時に書く（`docs/99` 実装フェーズ）。本ADRは形（方針）の確定。
