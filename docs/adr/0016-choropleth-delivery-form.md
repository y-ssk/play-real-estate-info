# ADR-0016: 色分け配信方式＝値とジオメトリを分離(継ぎ目)・初手GeoJSON→行き先ベクタタイル(一体型ST_AsMVT)

- ステータス: 承認
- 日付: 2026-06-24
- 関連: `docs/99_decision-register.md`（優先3 受け渡し仕様・3-1 API設計方針）／`docs/02_architecture.md` §6バックエンド・§7フロント・§9共通前提／`ADR-0013`（一体型1プロセス・MapLibre GL JS）／`ADR-0015`（縦持ち集計テーブル・メッシュ移行は`unit_kind`差し替え）／`ADR-0014`（配信時3857へ変換）／学習メモ `docs/notes/2026-06-24-vector-tiles-vs-geojson.md`

## なぜ（背景・課題）
表示3モードのうち**色分け（市区町村ポリゴンを単一指標で塗る）**のデータを、PostGISからブラウザ(MapLibre)へどう運ぶかを決める。ここがレスポンスの形を決め、下流（クエリ層3-2・FE取得3-3）を縛る背骨。

オーナーの問い＝「いずれメッシュ(v1)でタイル化するなら、MVPでGeoJSONを作るのは作り直しの無駄では？」。これに答えるため案を一枚岩で比べず層に分解した。色分けは〔データモデル・値を引くSQL・値API・色付け式〕の約8割が運び方に依らず共通で、**差が出るのは「ジオメトリ配信」と「FEのソース種別」だけ**だと分かった。

- `ST_AsGeoJSON`（全件・テキスト・経度緯度）＋ MapLibre **geojson source**（全部を記憶に持つ）
- `ST_AsMVT`（タイルz/x/yごと・バイナリpbf・タイル内0〜4096局所座標）＋ **vector source**（見えるタイルだけ取得）

概念の解説は学習メモ `2026-06-24-vector-tiles-vs-geojson.md` に分離。

## 結論（決定）

### (i) 継ぎ目を固定＝値とジオメトリを別経路に（運び方に依らず必須）
形に値を埋め込む素朴形は採らない。値APIを形から分離し、FEは `setFeatureState` で `feature_id`(=5桁コード)結合して塗る。
- 形：`GET /api/choropleth/geometry?pref=13` → 境界（値なし）
- 値：`GET /api/choropleth/values?metric=<key>&pref=13` → `{ "13104": 0.23, ... }`（縦持ち`metric_value`を`metric_key`で引く・`ADR-0015`）
- カルテ：`GET /api/karte?unit=13104` → 当該単位の全指標
- 色付け式（値→色の`interpolate`）は運び方に依らず共通。

### (ii) 初手＝B（`ST_AsGeoJSON` ＋ geojson source）
最初のETL縦スライスは `ST_AsGeoJSON`（境界は`ST_Simplify`で軽量化）＋ geojson source で通す。
- 根拠：最初の縦スライスの仕事は**データが正しく通ることの証明**＝Feedback層1（データの正しさ・最優先）。GeoJSONは人が読める・`curl`で目視でき、「データが正しいか」を「タイル算が正しいか」から切り離せる。MLIT取得＋変換＋PostGIS投入の未知に、タイル座標(z/x/y・クリップ・pbf)の未知を同時に乗せない。

### (iii) 行き先＝A（`ST_AsMVT` を一体型のGoサーバ内ハンドラで）に固定
データが信頼できた段で、形の配信を `ST_AsMVT`＋vector sourceへ局所差し替えしAへ到達する。タイルは3857で作る（`ADR-0014`・`ST_TileEnvelope`既定3857）。
- 根拠：タイル化はメッシュ(v1の本丸方向)でいずれ必須／本丸＝地図表現を正しい形に仕上げる／静的な境界タイルはHTTPキャッシュが効く。(i)の継ぎ目を入れてあるので、差し替えは「`geometry`ハンドラの中身＋FEのsource種別1行」に限定され、値API・結合・色式・データモデルは無傷（＝作り直しではない）。
- **タイル機構は自前`ST_AsMVT`ハンドラ**（同一Goプロセス）。`pg_tileserv`/`martin`等の別プロセスは**一体型(`ADR-0013`)に反する**ため不採用。

### (iv) 重ね（参考・MVP）
点（駅・地価地点・施設）は「表示中の市区町村に絞ったGeoJSON」で足りる。塗り絵の面（ハザード・用途地域）は`docs/02`方針どおりタイル配信だが、MLITのタイル提供有無は各レイヤー実装時にIF定義で確認（憶測しない）。

## 検討した代替案と捨てた理由
- 素朴な案1（値も形も1つのGeoJSONに詰める）… 値の埋め込みごと捨てることになり「無駄な作り直し」が現実に発生。継ぎ目(i)で回避。
- 純A一気（初手から`ST_AsMVT`）… MVP最初の縦スライスで、データ正しさの未知とタイル座標の未知が同時に乗り、白画面の切り分けが困難。`ST_AsGeoJSON`のデバッグ口併設なら可だったが、初手の隔離性でBが優る。行き先がAなのは変わらない。
- 案3（値を焼き込んだタイル）… 指標×ズームでタイル組み合わせが爆発、値更新で再生成。MVPに過剰。
- 別プロセスのタイルサーバ（pg_tileserv/martin）… プロセスが2つになり単一バイナリ・1プロセス配備（一体型）と食い違う。

## 影響（結果・トレードオフ）
- 優先3-1（API設計方針＝粒度・タイル/データ分離）が確定。残る優先3は 3-2 クエリ層・3-3 状態管理/取得・3-4 ベースマップ。
- 実装に「継ぎ目」を課す＝値APIと形APIを最初から分ける（FEは`setFeatureState`結合前提）。
- ETL縦スライスはタイルを待たずGeoJSONで端から端まで通せる（層1検証が見やすい）。
- 行き先Aへの差し替え時期は「データが信頼できた段／遅くともメッシュ移行前」。`ST_AsGeoJSON`のデバッグ口はA到達後も層1検証用に残す価値あり。
- エンドポイントの最終粒度（クエリ引数・絞り込み条件の渡し方）は 3-2／実装着手時に詰める。本ADRは配信の形（方針）の確定。
