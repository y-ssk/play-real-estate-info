# ADR-0017: クエリ層＝pgx土台・sqlc既定・生SQLは名前のつく例外のみ（ハイブリッド）

- ステータス: 承認
- 日付: 2026-06-24
- 関連: `docs/99_decision-register.md`（優先3 受け渡し仕様・3-2 クエリ層）／**お作法の最新は `docs/backend-conventions.md` §1**（本ADRは凍結記録・取り決めの引き先ではない）／`docs/02_architecture.md` §6／`ADR-0013`（一体型1プロセス・マイグレ生SQL・ORM自動マイグレ不採用）／`ADR-0015`（縦持ち`metric_value`）／`ADR-0016`（配信の形＝値取得・geometry・タイル）／`ADR-0012`（絞り込み＝動的）／学習メモ `docs/notes/2026-06-24-query-layer-approaches.md`

## なぜ（背景・課題）
`ADR-0016` でレスポンスの形が決まり、それを吐くSQLを Go からどう書くかを決める必要が出た。`internal/store/` に置くアクセス方式の選定。マイグレは生SQL確定（`ADR-0013`）だが、クエリ層は未定だった。

本プロジェクトのクエリは**静的が多数**（値取得・カルテ・geometry・タイル）で、**動的は絞り込み1系統**（`ADR-0012` の可変条件）。加えてETLは**大量一括投入**がある。型安全（層1＝データの正しさの土台）と、動的の柔軟さと、PostGIS関数（`ST_AsMVT`等）の素直な記述を、同時に満たす形が要る。

## 結論（決定）
**ハイブリッド**：
- **接続の土台＝`pgx`**（Goの現行事実上標準。PostGISバイナリ型・`COPY`・性能で有利。`database/sql`+`lib/pq`は採らない）。
- **既定＝`sqlc`**：静的クエリ（多数）を型安全に。SQLは自分で書くので PostGIS関数も書け、学びにもなる。生成物は内部で pgx を呼ぶだけで実行時依存なし＝一体型（単一バイナリ）を崩さない。
- **生SQL（pgx直）は名前のつく例外のみ**：例外1=実行時に形が変わる（動的WHERE）、例外2=大量一括投入（`CopyFrom`）、例外3=sqlcが表現できない構文。
- **ORM不採用**。

**お作法（既定＋3例外の芯・アンチパターン・デザインパターン・テスト粒度・レビュー5問・例外台帳）は生きた文書 `docs/backend-conventions.md` §1 に置き、本ADRには凍結しない**（最新の取り決めは同文書を見る）。運用へ取り込むため `CLAUDE.md` ドキュメント地図と `implementer`/`reviewer` の「最初に読む」へ配線する。

## 検討した代替案と捨てた理由
- **生SQL一本**（pgx直のみ）… 着手は軽いが、静的が多数なのに型安全（列名・型をビルド前に検査）を捨てるのが惜しい。`Scan` の定型コードと実行時までtypoに気づけない弱点。＝有効な対案だが、型安全の利得が大きい本件では既定にしない（MVP最初を最軽量にしたい場合の昇格元としては可）。
- **クエリビルダ主体**（squirrel等）… 動的が主なら映えるが、本件は静的多数で冗長。PostGIS関数は結局文字列埋め込みになり旨みが減る。動的1系統は生SQLで足りる。
- **ORM**（gorm/ent）… geometry（空間型）を素直に扱えず`ST_*`はraw埋め込みになり意味が薄れる。自動マイグレはPostGIS拡張・GiST索引・SRID指定で不都合（`ADR-0013`既決）。SQLが隠れ学びも薄い。

## 影響（結果・トレードオフ）
- 優先3-2 が確定。残る優先3は 3-3 状態管理/取得・3-4 ベースマップ。
- **お作法の置き場を確立**＝凍結のADRと、育つ規約文書（`backend-conventions.md`）を分離。規約類は今後もこの器へ集約。
- **運用への配線**＝CLAUDE.md地図＋implementer/reviewerへ参照を追加（決定が実装・レビューで実際に参照される仕組み）。
- 2方式同居の線引き規律が要るが、基準は単純（条件が固定=sqlc／可変=生SQL）。
- 実装着手時に詰める残件：sqlc の geometry 型override（`sqlc.yaml`）、縦持ち`metric_value`での動的絞り込みの具体SQL（`EXISTS`/`HAVING`構成）。本ADRは方式の確定。
