## なぜ（背景・課題）

価値定義（優先1）完了後、**重い優先2（共通結合基盤）に集中する前に、実装の足場を一括で固める**方針（`docs/99` の「前倒し（軽い確認バッチ）」）。地図エンジン・FE器・ローカル環境などは個別トリガーが「実装着手時」だったが、順番に縛らず前倒しでまとめて確定する。各項目は周辺＝薄く、本丸（ETL・データ・地図表現）に集中するための土台固め。

## 結論（決定）

1. **認証／ユーザー機能＝MVPは無し（匿名利用）**。ピン留めはブラウザ保存（localStorage、`ADR-0012`）。端末をまたぐ保存（アカウント＋サーバー）はv1。書き込み資産が薄く、認証は周辺＝最小化。

2. **地図エンジン＝MapLibre GL JS**（React 連携は `react-map-gl/maplibre`）。
   - データ駆動スタイル（式）で、見る属性を差し替えるだけで分野の色分けを切替（再取得不要、`ADR-0005`）。
   - ベクタタイルで拡大に強く、単位を市区町村→メッシュに差し替えても描画側は不変（`ADR-0006`）。
   - トークン不要・公開仕様＝透明性。Mapbox GL JS（トークン必須・課金）を避ける根拠。

3. **FE器＝React。ビルド＝Rsbuild（Rspack）。テスト＝Jest＋React Testing Library**。
   - Jest：構造的に待ち受けサーバを持たず、Vitest で報告された「テスト用サーバ経由」の攻撃面を持たない。長期に使われ安定。ビルドツールから独立。
   - Rsbuild：webpack 互換（エコシステムの厚みを継承）かつ Vite 系譜から距離を置ける＝堅牢志向に素直。
   - E2E は Playwright を想定（自動E2Eは「MVP後」保留のまま）。
   - **この決定は可逆**：アプリ本体（React のコード）はビルドツールにほぼ依存しないため、将来の乗り換えは設定差し替え中心で低コスト。今ここで完璧に当てる必要はない、と明記する。

4. **全体構成＝一体型（Go が FE ビルド成果物を `embed` して配信）を追認**（`docs/02` 既定）。単一成果物・CORS不要・FE/BE版ずれ無し・運用最小。**FEディレクトリは機能単位（feature-based）**：`app/ features/ components/ lib/ styles/ test/`。思想（Screaming Architecture・凝集・依存の一方通行・FSDとの距離）は学習メモ参照。

5. **ローカルDB＝PostGIS コンテナ**（`postgis/postgis` イメージ、Rancher Desktop で起動）。**マイグレーション＝生SQL（golang-migrate）**。スキーマの権威を SQL に置き、`geometry(...,SRID)`・GiST 空間索引・拡張を明示制御する。

## 検討した代替案と捨てた理由

- **認証をMVPから載せる** … 周辺を厚くする＝オーバーエンジニアリング。MVPは匿名＋localStorage で足りる。
- **Mapbox GL JS / Leaflet** … 前者はトークン必須・課金（透明性に反する）、後者はラスタ寄りでベクタの面塗り×切替が弱い。
- **Vite + Vitest** … Vitest は待ち受けサーバ経由の攻撃面が報告。Vite 自体も開発サーバ側に脆弱性報告の経緯。系譜から距離を置く判断。
- **Next.js（static export）** … 一体型Go配信とSSRが二重、static export では旨みが消え複雑さだけ残る。
- **型別ディレクトリ（components/hooks/utils…）** … 機能が増えると1機能の部品が複数フォルダに散り、変更が横断的＝育つと破綻。
- **フル Feature-Sliced Design（7層＋厳格規約）** … MVP には過剰＝核だけ軽く採る。
- **FE分離ホスティング（CDN等）** … CORS・2系統運用・別課金。首都圏規模でCDNは必須でない。
- **ORM の自動マイグレ（GORM AutoMigrate 等）** … PostGIS 空間型・空間索引が苦手で結局 raw 併用＝二重化、暗黙のスキーマ変更が事故源。

## 影響（結果・トレードオフ）

- `docs/99` の保留事項のうち **認証要否・地図エンジン・FEの器・全体構成（一体型）追認・ローカル環境ツール** を「確定」へ移す。確定索引に本ADRを追加。
- **残す保留**（実装着手時）：**クエリ層**（Goからの DB アクセス方式＝生SQL／sqlc／クエリビルダ。マイグレを生SQLにしても両立、sqlc 候補）・**ベースマップ調達先**・**状態管理／データ取得ライブラリ**。
- FE変更でも Go 再ビルドが要る（開発時は FE dev サーバで高速プレビュー、本番のみ embed の二段構え）。
- ビルドツール（Rsbuild）は可逆な決定として記録（将来乗り換え可）。
- 次は **優先2（共通結合基盤）** に集中。
