# ADR-0003: ブランチ戦略 — feature → dev → main（main 直コミット禁止）

- ステータス: 承認
- 日付: 2026-06-23
- 関連: `CLAUDE.md` / `99_decision-register.md` / リモート `origin`（github.com/y-ssk/real-estate-map）

## なぜ（背景・課題）
個人開発でも `main` へ直接コミット/プッシュするのは健全でない。変更を隔離し、
キリのいい**小さな単位でレビュー（PR）して取り込む**ことで、考慮漏れ・巻き戻しに強くする。
PR は重くなる前に区切る。

## 結論（決定）
- `main`・`dev` はともに**保護線**。**直接の commit も push も禁止**。更新は PR/merge 経由のみ。
  - `main`: リリース相当の安定線。
  - `dev`: 統合線。feature からの PR/merge でのみ更新。
- `feature/<topic>`: 作業ブランチ。コミットはここだけで行い、まとまりごとに `dev` へ PR（小さく保つ）。
- 取り込み順: **feature → dev → main**。PR は GitHub（`origin`）で出す。
- 権限（2026-06-23 更新。下記「## 更新」参照）:
  - feature への commit / push、PR 作成は **オーナーの都度許可なく** 行ってよい。
  - `dev` / `main` への直接 push は禁止（保護線。更新は PR/merge 経由のみ）。
  - **`feature → dev` の取り込み（merge）は AI（オーケストレーター）が実行してよい**（PR 作成→マージ→マージ済みブランチ整理まで一貫）。
  - **`dev → main` の取り込み（merge）は引き続きオーナーが承認/実行**する（本番相当の門番はオーナー）。

## 検討した代替案と捨てた理由
- `main` 直コミット（立ち上げ期の現状）: 隔離もレビュー点もなく、考慮漏れ・巻き戻しに弱い → 却下。
- `dev → main` の2層のみ（最小）: feature 隔離が無く複数論点が `dev` に混ざる → 最小許容だが既定は3層。

## 影響（結果・トレードオフ）
- 以降の作業は feature ブランチで行い、`main`/`dev` は PR/merge 経由でのみ進む。
- 立ち上げ期のコミット（`753f1c1`..`fa28a24`）は `main` 直積みだった。これはベースラインとして残し、以降は本戦略に従う。

## 更新（2026-06-23）: `feature → dev` の merge 権限を AI へ委譲
- 背景: IF定義収集のように feature→dev の PR/merge が高頻度で発生し、その都度オーナーが merge を実行するのは流れを止める。dev は統合線であり巻き戻しも容易（本番ではない）。
- 変更: `feature → dev` の merge を **AI（オーケストレーター）が実行可**に。`dev → main` は従来どおり**オーナー承認/実行**を維持（保護線の本丸 main の門番はオーナーに残す）。
- トレードオフ: dev への取り込み判断を AI が持つぶん、PR は引き続き小さく・ブロック単位で出し、レビュー可能性を保つ。問題があれば dev で revert する。
