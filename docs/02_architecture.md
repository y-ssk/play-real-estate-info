## 1. 構成の全体像

**ETL＋分析を土台に、タイル配信を乗せたハイブリッド。** 一体型（Goが1プロセスで担う）。

- **取り込み（ETL）**：突き合わせ・集計が要るデータを、事前に自前DB（PostGIS）へ取り込み正規化する。
- **タイル配信（プロキシ）**：地図に重ねるだけの “塗り絵レイヤー” は、取り込まずキャッシュ配信する。
- **一体型**：GoサーバーがデータAPI・タイル配信・ビルド済みフロント配信をまとめて担う。デプロイは1プロセス。Goの `embed` で単一バイナリ同梱も可。分離（SPA＋APIサーバー）は全国化・本格運用が必要になってから移行。

なぜ自前DBか：MLIT APIは「連続実行を避ける」制約があり、ユーザー操作のたびに叩く設計と相性が悪い。事前にまとめて取り込み、ユーザーには自前DBから返す。

バックエンド言語は **Go**（採用理由はオーナー自身で言語化予定。`99_decision-register.md`）。

## 2. データフロー

```
[定期] ingest : MLIT API → 変換 → PostGIS（市区町村単位に正規化・出典付きで保持）
[随時] api    : 絞り込み条件 → PostGISで空間クエリ＋集計 → 地図/カルテ用に返却
[随時] tiles  : ハザード/用途地域などのGISレイヤー → キャッシュして配信
```

## 4. 取り込み（ETL）の設計要件

API制約とデータ品質を吸収する仕掛けを最初から組み込む。

- **レート制御**：リクエスト間隔を空ける／スロットリング（Goの `time` / レートリミッタ）。「連続実行を避ける」を機械的に担保。
- **冪等性**：同じ取り込みを再実行しても二重にならない。
- **再開可能性**：途中で止まっても続きから再開できる。
- **出典の保持**：各データにMLIT／国土数値情報の出典を紐づけて保存（UI表示は法的要件）。
- **欠損の検知**：市区町村単位でデータが欠ける場合に “無い” ことを検出（UIの「データなし」表示につなぐ）。

> 取り込みの「正しさ」をどう検証するか（テスト・値域チェック等）は `04_harness.md`（Feedback層1）で定義する。

## 5. 全国化の方針

- 取り込みは市区町村コード単位で回る。**対象とする市区町村コードを「設定リスト」として外出し**する。
- MVPは首都圏9都県のコードのみを対象にする。
- 全国化は **設定リストにコードを追加するだけ**で到達でき、アーキテクチャは変更しない（収集時間は増える）。

## 6. バックエンド構成（Go）

ディレクトリ構成の素案（ETL＋分析型を土台に、タイル配信を足す）：

```
.
├── cmd/
│   ├── api/main.go      # 随時：分析/カルテAPI＋タイル配信＋フロント配信
│   └── ingest/main.go   # 定期/手動：取り込みバッチ
├── internal/
│   ├── mlit/            # MLIT APIクライアント（レート制御込み）
│   ├── ingest/          # 取り込み・変換（JSON/GeoJSON → PostGIS）
│   ├── store/           # PostGISリポジトリ（空間クエリ）
│   ├── analysis/        # 集計・指標算出
│   ├── tiles/           # タイルのプロキシ＋キャッシュ
│   └── handler/         # APIハンドラ
├── migrations/          # PostGISスキーマ（PostGIS拡張・空間index）
├── web/                 # フロント（ビルド成果物をGoが配信）
└── go.mod
```

- **器（フレームワーク）**：未確定。Reactを想定するが「過去に使った」ではなく評価軸（透明性→普及度→部品→レスポンシブ→地図統合）で確定する（`99_decision-register.md`）。

## 8. 空間単位

- **MVP：市区町村粒度**（取得が軽く、検証しやすい）。
- **v1：メッシュ粒度（250m〜）へ降ろす**。異種データの空間結合が増えるため、市区町村で仕組みを完成させてから移行。
- **集計はメッシュ移行を妨げない形に統一**（`ADR-0006`）：指標は「単位ポリゴンに空間結合して集計」（例：該当面積率＝交差面積÷単位面積）を共通形とし、単位ポリゴンを市区町村↔メッシュで差し替えれば同じ計算が効くようにする。全分野に適用。

## 9. 共通前提

- **座標系**：JGD2011前提。フロント（地図）はEPSG:4326/3857で扱うため必要に応じ変換。
- **開発環境**：WSLネイティブFS上にリポジトリを置く（`/mnt/c` 越しは不可）。Rancher Desktop（コンテナ化は本格化してから）。
- **データの鮮度**：MLITは年度更新。取り込みの回し直し運用は `99_decision-register.md`（保留・ETL基盤着手時）。
