## 1. 構成の全体像

**ETL＋分析を土台に、タイル配信を乗せたハイブリッド。** 一体型（Goが1プロセスで担う）。

- **取り込み（ETL）**：突き合わせ・集計が要るデータを、事前に自前DB（PostGIS）へ取り込み正規化する。
- **タイル配信（プロキシ）**：地図に重ねるだけの “塗り絵レイヤー” は、取り込まずキャッシュ配信する。
- **一体型**：GoサーバーがデータAPI・タイル配信・ビルド済みフロント配信をまとめて担う。デプロイは1プロセス。Goの `embed` で単一バイナリ同梱も可。分離（SPA＋APIサーバー）は全国化・本格運用が必要になってから移行。

なぜ自前DBか：MLIT APIは「連続実行を避ける」制約があり、ユーザー操作のたびに叩く設計と相性が悪い。事前にまとめて取り込み、ユーザーには自前DBから返す。

バックエンド言語は **Go**（採用理由はオーナー自身で言語化予定。`99_decision-register.md`）。

## 2. データフロー

```
[定期] ingest : MLIT API → 変換 → PostGIS（市区町村単位に正規化・出典付きで保持）
[随時] api    : 絞り込み条件 → PostGISで空間クエリ＋集計 → 地図/カルテ用に返却
[随時] tiles  : ハザード/用途地域などのGISレイヤー → キャッシュして配信
```

## 4. 取り込み（ETL）の設計要件

API制約とデータ品質を吸収する仕掛けを最初から組み込む。

- **レート制御**：リクエスト間隔を空ける／スロットリング（Goの `time` / レートリミッタ）。「連続実行を避ける」を機械的に担保。
- **冪等性**：同じ取り込みを再実行しても二重にならない。
- **再開可能性**：途中で止まっても続きから再開できる。
- **出典の保持**：各データにMLIT／国土数値情報の出典を紐づけて保存（UI表示は法的要件）。
- **欠損の検知**：市区町村単位でデータが欠ける場合に “無い” ことを検出（UIの「データなし」表示につなぐ）。**「データなし（対象外・未整備）／該当なし＝値が0／秘匿（小人口で非公開）」の3つを区別**して保持する（`ADR-0011`。「危険ゼロ」と「未調査」を混同させない）。

> 取り込みの「正しさ」をどう検証するか（テスト・値域チェック等）は `04_harness.md`（Feedback層1）で定義する。

## 5. 全国化の方針

- 取り込みは市区町村コード単位で回る。**対象とする市区町村コードを「設定リスト」として外出し**する。
- MVPは首都圏9都県のコードのみを対象にする。
- 全国化は **設定リストにコードを追加するだけ**で到達でき、アーキテクチャは変更しない（収集時間は増える）。

## 6. バックエンド構成（Go）

ディレクトリ構成の素案（ETL＋分析型を土台に、タイル配信を足す）：

```
.
├── cmd/
│   ├── api/main.go      # 随時：分析/カルテAPI＋タイル配信＋フロント配信
│   └── ingest/main.go   # 定期/手動：取り込みバッチ
├── internal/
│   ├── mlit/            # MLIT APIクライアント（レート制御込み）
│   ├── ingest/          # 取り込み・変換（JSON/GeoJSON → PostGIS）
│   ├── store/           # PostGISリポジトリ（空間クエリ）
│   ├── analysis/        # 集計・指標算出
│   ├── tiles/           # タイルのプロキシ＋キャッシュ
│   └── handler/         # APIハンドラ
├── migrations/          # PostGISスキーマ（生SQL＝golang-migrate。PostGIS拡張・空間index）
├── web/                 # フロント（ビルド成果物をGoが embed 配信）
└── go.mod
```

- **ローカルDB**：PostGIS コンテナ（`postgis/postgis` イメージ・Rancher Desktop）。**マイグレーションは生SQL（golang-migrate）**＝スキーマの権威をSQLに置き `geometry(...,SRID)`・GiST空間索引・拡張を明示制御。ORMの自動マイグレは空間データで不都合のため不採用（`ADR-0013`）。

**API設計方針（色分け配信・`ADR-0016`で確定）**：**値とジオメトリを別経路に分離（継ぎ目）**＝形 `GET /api/choropleth/geometry`、値 `GET /api/choropleth/values?metric=<key>`（縦持ち`metric_value`を引く）、カルテ `GET /api/karte?unit=<5桁>`。FEは `setFeatureState` で5桁コード結合し色付け（色式は運び方に依らず共通）。**初手＝`ST_AsGeoJSON`＋geojson source**（最初のETL縦スライスはデータ正しさ＝層1を目視できる形で隔離）→ **行き先＝`ST_AsMVT` を本サーバ内ハンドラで＋vector source**（タイルは3857・§9）。タイルは自前`ST_AsMVT`で持ち、`pg_tileserv`/`martin`等の別プロセスは一体型に反するため不採用。

**クエリ層（`ADR-0017`で確定）**：**ハイブリッド**＝接続土台 `pgx`／既定 `sqlc`（静的クエリ多数を型安全に・PostGIS関数も書ける）／生SQLは名前のつく例外のみ（動的WHERE・大量投入`CopyFrom`・sqlc非対応構文）。ORM不採用。**実装/レビューのお作法（既定＋3例外・アンチ/デザインパターン・テスト粒度・レビュー5問・例外台帳）は生きた文書 `docs/backend-conventions.md` §1**（ADRは凍結記録で参照先にしない）。

未確定（実装着手時に決定。`99_decision-register.md`）：
- エンドポイントの最終粒度（クエリ引数・絞り込み条件の渡し方）※配信の形は `ADR-0016` で確定
- sqlc の geometry 型override（`sqlc.yaml`）・縦持ち`metric_value`での動的絞り込みの具体SQL（`EXISTS`/`HAVING`）※方式は `ADR-0017` で確定

## 7. フロント構成

- **スタイル土台**：Tailwind ＋ melta-ui（MIT）の設計仕様書を取り込んだデザインシステム。UI規約は `DESIGN.md`。melta-uiは器非依存なので、フロント器の確定を待たずに取り込み・運用できる。
- **器・ビルド・テスト（`ADR-0013`）**：器＝**React**／ビルド＝**Rsbuild（Rspack）**／テスト＝**Jest＋React Testing Library**（E2EはPlaywright・MVP後）。Vitestは攻撃面回避で不採用、Vite系譜から距離を置く。ビルドツールは**可逆な決定**（後で乗換可）。
- **地図エンジン（`ADR-0013`）**：**MapLibre GL JS**（`react-map-gl/maplibre`）。データ駆動スタイルで分野切替、ベクタタイルでメッシュ移行に強い、トークン不要＝透明性。
- **ディレクトリ構成（機能単位 / feature-based・`ADR-0013`）**：`web/src/` = `app/`（起動・プロバイダ・全体レイアウト）／`features/`（map・filters・karte・comparison・pins）／`components/`（melta-ui取り込み層）／`lib/`（APIクライアント・地図初期化・共通型・出典/欠損）／`styles/`（tokens）／`test/`。思想は学習メモ `docs/notes/2026-06-24-fe-architecture-feature-based.md`。
- **地図UI**：③開閉式パネル（PC）。閉＝地図没入／開＝固定領域で読み込み。モバイルはボトムシート展開（PC実装後）。詳細は `DESIGN.md`。
- **PC/モバイル両対応**が前提。

未確定（実装着手時に決定）：
- ベースマップ（地図下地タイル）の調達先（自前／外部）※MLITとは別の依存
- 状態管理・データ取得ライブラリ
- 地図とフロントの状態管理の統合（開閉状態を含む）

## 8. 空間単位

- **MVP：市区町村粒度**（取得が軽く、検証しやすい）。
- **v1：メッシュ粒度（250m〜）へ降ろす**。異種データの空間結合が増えるため、市区町村で仕組みを完成させてから移行。
- **集計はメッシュ移行を妨げない形に統一**（`ADR-0006`）：指標は「単位ポリゴンに空間結合して集計」（例：該当面積率＝交差面積÷単位面積）を共通形とし、単位ポリゴンを市区町村↔メッシュで差し替えれば同じ計算が効くようにする。全分野に適用。
- **結合の的（共通結合基盤の前半・`ADR-0014`）**：単位ポリゴンの境界＝**国土数値情報 行政区域データ(N03)**（`XIT002`はコードのみで境界を持たないため別調達）。結合キー＝**5桁市区町村コード**（`XIT002.id`を権威、N03 `N03_007`・各レイヤーを5桁へ。コードで結合し名称ゆれは表示用。年度固定・値域チェック=上2桁がarea一致）。**集計の最小単位＝区粒度**（政令市は区のまま、市まとめはUI側v1）。
- **空間結合の具体形（共通結合基盤の後半・`ADR-0015`）**：**事前集計（マテリアライズ）**＝取り込み時に「単位×指標」へ書き出す（オンデマンド交差はしない）。**縦持ち集計テーブル** `metric_value(unit_id, unit_kind, metric_key, value_num, unit, data_status, source, vintage)`（指標追加=行追加、`unit_kind`差し替えでメッシュ移行、`ADR-0011`のデータなし3区別/出典/年度を行に同居）。演算＝**ポリゴン:交差面積按分／点:内包・件数／メッシュ:重心法**（按分はパターンごとに異なるのが正しい）。カテゴリ系（用途地域構成比等）は別表。考え方の解説は学習メモ `docs/notes/2026-06-24-spatial-join-aggregation.md`。

## 9. 共通前提

- **座標系（`ADR-0014`で確定）**：**保存SRID＝EPSG:6668（JGD2011）に統一**。取り込み時に JGD2000(4612, XKT017/019)→`ST_Transform`→6668、CRS84(XKT027)は6668として取り込む（WGS84↔JGD2011の実用差は小）。**面積率は`geography`で算出**（比なので投影差に頑健、厳密実面積が要る場面のみ平面直角座標系6677等へ投影）。**配信（タイル／レスポンス）時に3857**（必要なら4326）へ変換し、MapLibre側は触らず取り込み側で吸収。
- **開発環境**：WSLネイティブFS上にリポジトリを置く（`/mnt/c` 越しは不可）。Rancher Desktop（コンテナ化は本格化してから）。
- **データの鮮度**：MLITは年度更新。取り込みの回し直し運用は `99_decision-register.md`（保留・ETL基盤着手時）。
