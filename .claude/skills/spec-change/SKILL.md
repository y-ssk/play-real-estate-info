# 仕様変更の依頼と反映（spec-change）

> 仕様変更を場当たりにせず、**正の仕様（どこを見れば正か）を更新し、背景（なぜ変えたか）を残す**ための導線。
> 起動＝`/spec-change`（オーナーの仕様変更依頼／層4レビュー指摘を起こすとき）。運用が形骸化しないよう、仕様を変えるときは必ず本導線を通す。

## 正の仕様の所在（どこを見れば正か）

| 対象 | 正のドキュメント |
|---|---|
| スコープ（やる/やらない/保留） | `docs/01_project-overview-scope.md` |
| 画面・機能・遷移・UX・導線 | `docs/05_screens-and-flows.md` |
| UI・視覚・色・共通部品 | `DESIGN.md`（＋共通部品の実装 `web/src/components`） |
| データ・アーキ・配信 | `docs/02_architecture.md` |
| 決定の索引・保留・実装スライス（待ち行列） | `docs/99_decision-register.md` |
| 凍結された判断の根拠 | `docs/adr/`（最新の取り決めは生きた文書、ADRは凍結根拠） |

**仕様変更は必ず該当する“正”を更新し、背景を ADR/`docs/99` に残す。** PR コメントは経緯の補助であって正ではない。

## 依頼テンプレート（この枠で出す）

オーナーが書く、または口頭/チャットの依頼を私（オーケストレーター）が本枠に起こす：

```
対象（画面/機能/スライス）：
現仕様（正の所在＝docs/05 §… / DESIGN §… 等）：
変更したいこと：
なぜ（背景・きっかけ＝層4レビュー指摘・新たな気づき 等）：
影響範囲（他画面/データ/DESIGN/既存スライス）：
反映先（更新する正の doc）＋ ADR 要否：
実装の単位（スライス化）：
```

## 導線（手順）

1. **依頼を起こす**：上テンプレートを埋める。不足は壁打ちで埋める。大きい判断は「選択肢＋理由＋トレードオフ＋捨てる案」を出しオーナーの決定を待つ（`CLAUDE.md` 進め方）。
2. **決定を記録**：凍結する価値のある判断は ADR を新設（「なぜ」＝この依頼/指摘）。状態は `docs/99` の確定索引／保留へ。
3. **正の仕様を更新**：上表の該当 doc を同じ変更で更新する（`docs/04` 変更管理：根拠と実態を一致）。
4. **待ち行列へ**：実装の単位を `docs/99`「実装スライス」へ積む。
5. **実装→検証→PR**：実装役→reviewer（層1〜3）。**層4レビューの指摘と解決は PR コメントに記録**（経緯の補助）。仕様判断になったものは 1〜3 へ戻して正へ反映する。

## 禁止

- テンプレートを経ない場当たりの仕様変更（形骸化の元）。
- 正の doc を更新せず、コードや PR コメントだけで仕様を変えること。
- 「周辺＝薄く」を理由に、ユーザーが触る画面の骨格・共通部品・導線の設計を省くこと（薄く＝作り込まない、であって設計しない、ではない）。

> 関連：記録様式（ADR・学習メモ）＝`record-format`／コミット・PR 様式＝`commit-pr-format`／全量点検＝`docs/04` §8。
