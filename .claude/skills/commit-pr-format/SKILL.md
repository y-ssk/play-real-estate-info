# コミット / PR の様式（確定・Step D）

> 参照チェーン：`CLAUDE.md` → `docs/commit-pr-format.md` → 本スキル。
> 様式の実体はここに隠蔽する。ADR・学習メモは別スキル `record-format`。

## 方針（`docs/04_harness.md` 第8節・`CLAUDE.md`）
- 「なぜ」を厚く残す（本丸＝ETL・データモデリング・地図表現）。周辺は薄く。
- コミットは意味のある最小単位。**コードと文書は同じ変更で更新**する。
- ADR が整備されたら「記録:」に ADR 番号を紐づける（現状は未付与可）。

## コミットメッセージ

```
<type>: <一言要約>

なぜ:
- <背景・目的>

内容:
- <何をしたか（箇条書き）>

記録: <関連ADR番号 / 同時更新した文書 / なし>
```

- `type` は下記「type（種別）の使い分け」表（コミット・PR 共通の1情報源）。
- 1行目は要約のみ（72字目安）。本文との間に空行。

## type（種別）の使い分け（コミット・PR 共通）

| type | 使う場面 |
|---|---|
| `feat` | 新機能・新指標・新スライスの機能追加（面塗り指標／絞り込み／配色体系 等） |
| `fix` | バグ・不具合の修正（層4指摘の是正を含む＝挙動の誤りを正す） |
| `docs` | ドキュメント/ADR/仕様/バックログのみの変更（コードなし） |
| `refactor` | 挙動を変えない内部整理（継ぎ目・命名・構造の整理） |
| `test` | テストの追加・修正のみ |
| `chore` | 依存・ビルド・`scripts`・設定など雑務（プロダクト挙動に影響しない） |

- 任意で `perf`（性能改善）／`style`（整形のみ・意味変更なし）。
- 迷ったら「利用者から見た挙動が変わるか」で分ける＝変わる→`feat`/`fix`、変わらない→`refactor`/`chore`/`docs`。

## PR 説明

### PRタイトル
- **コミット1行目と同じ `<type>: <要約>`** を必ず付ける（PRタイトルにも接頭辞を必須化＝コミットと揃え、squash 時にそのままコミットになっても活きる）。1PR=1スライスゆえ**主たる type を1つ**選ぶ。スコープ任意（`feat(fe):`／`feat(etl):`／`feat(be):`）。
- 既に merged のタイトルは遡及しない（履歴）。今後統一する。**implementer 依頼と reviewer チェックにこの規約を含める**（無自覚な崩れを規約で塞ぐ）。

### 本文テンプレ
> origin 接続済み・PR 運用中。将来 `.github/PULL_REQUEST_TEMPLATE.md` へ転写すると GitHub で自動適用される。

```
## 概要
<このPRで何を達成するか（1〜3行）>

## なぜ
<背景・目的。本丸は厚く、周辺は薄く>

## 変更内容
- <主な変更>

## 記録
- 関連ADR: <番号 / なし>
- 同時更新した文書: <ファイル / なし>

## 確認（Feedback 4層・`docs/04_harness.md` 第5節）
- [ ] 層1 データの正しさ（ETL時。該当すれば）
- [ ] 層2 lint / 型 / test
- [ ] 層3 UI規約（UI変更時）
- [ ] 層4 目視確認（該当すれば）
```
